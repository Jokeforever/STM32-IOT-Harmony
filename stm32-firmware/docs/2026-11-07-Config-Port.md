# 配置存储与时基接口：学习说明及本轮验收

代码与编译日期：2026-11-07。验收同步日期：2026-11-08，本轮五项用户检查全部通过。

## 这一步做了什么

此前mw_config.c直接包含i2c.h，调用EEPROM24C02_Read/Write和HAL_GetTick。
现在通过三个接口访问字节存储和毫秒时间，具体24C02与HAL调用集中在app_config_port.c。

配置核心继续负责槽选择、CRC、版本迁移、默认值、运行配置映射和延时保存。
平台适配负责把“在某偏移读取/写入若干字节、现在多少毫秒”转换为当前板子的调用。
这一轮只隔离硬件存储和时基，AppConfig业务映射依赖仍保留，不宣称整个配置模块已经完全解耦。

## 三个接口怎么理解

```c
uint8_t ConfigPort_Read(uint16_t offset, uint8_t *buffer, uint16_t length);
uint8_t ConfigPort_Write(uint16_t offset, const uint8_t *buffer, uint16_t length);
uint32_t ConfigPort_NowMs(void);
```

offset是配置区的字节偏移，不是I2C从机地址。
例如槽B偏移0x40，是EEPROM内部第64字节；芯片I2C地址仍由原驱动处理，不由配置核心填写。
buffer是读出/写入的数据，length是字节数，非0表示整个操作成功，0表示失败。

Write是同步完成接口：底层需要完成分页写入及等待写完成后才能报告成功。
若以后换成异步驱动，不能只把数据加入发送队列便返回成功，因为配置核心紧接着要读回校验。

NowMs提供自然回绕的uint32毫秒计数，当前直接转发HAL_GetTick。
不能直接换成RTC日历时间或秒计数，否则1000毫秒保存等待会失去原来的含义。

## 为什么接口地址比驱动地址宽

接口使用uint16偏移，让上层契约不受24C02的8位地址参数限制。
当前适配仍然只接受24C02的0～255字节区间；先验证，再转换为uint8_t交给原驱动。

C中把256直接强转成uint8_t会得到0。若先转换再检查，原本越界的请求可能误访问配置开头。
因此适配层同时拒绝：空缓冲、零长度、起始地址超范围、访问终点超范围。
端点检查使用uint32加法，不让16位加法回绕绕过范围判断。

这些是接口边界保护，配置核心实际仍只访问原来的两个槽；没有扩大EEPROM使用范围。

## 保存策略为什么保持不变

本轮只替换底层调用名称和头文件依赖，没有改动存储算法：

- Slot A仍从0x00开始，Slot B仍从0x40开始。
- v2记录仍48字节，CRC字段偏移44；v1仍32字节。
- 每槽读取仍是原64字节，保存仍写原48字节并读回验证。
- 仍在最后一次参数变化后等待1000ms再尝试保存。
- 保存失败保留待写状态，等待原来的重试间隔后再次处理。
- CRC、序号选择、默认值修正和v1迁移策略保持原样。
- 不要求清空已有EEPROM，有效的原阈值、模式和PID参数继续优先。

Config_Load、Save、MarkDirty、Process、IsDirty的对外声明不变，按键、网络、PID和采集模块不需要修改调用。
底层24C02的分页大小、ACK等待、I2C超时和OLED共用总线逻辑也没有修改。

## 将来更换平台怎么用

更换MCU时，优先检查app_config_port.c中的时间来源和存储驱动调用。
若继续使用24C02，保持当前字节语义、容量检查和同步完成语义即可继续复用配置核心。

更换为24C32等芯片时，需要使用正确的容量、内部字地址宽度和分页驱动。
不能只扩大容量宏，因为当前下层驱动的地址参数仍是uint8_t。
接口已经预留16位偏移，但新驱动本身仍需要实现和验证。

若改用内部Flash，还要另外设计擦除、对齐及双槽的物理布局，使写新记录时保留旧记录。
当前24C02上的64字节槽间隔不自动构成Flash上的独立擦除区域，不能只换函数名便认为迁移完成。

AppConfig运行参数映射和PID重置依赖没有在本轮进一步拆开，后续可以按需要逐步处理。
