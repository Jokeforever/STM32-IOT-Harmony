## 1. 为什么移动这两个函数

此前Display.c管理页面和数字，LED.c中的LED_Display绘制LED模式，bump.c中的Bump_Display绘制水泵模式。控制文件既要决定输出动作，又要知道OLED位置和字库编号。

本轮把两个模式绘制实现集中到Display.c。控制服务和显示服务继续共同读取当前AppConfig运行配置，各自完成控制和绘制职责，没有新建或缓存另一份模式状态。

```text
AppConfig当前运行配置
    ├─ LED.c / bump.c → PWM、GPIO、PID、灌溉控制
    └─ Display.c → 页面/读数/模式绘制 → 当前OLED驱动
```

本轮是实现位置的整理，现有页面外观与控制规则保持原样。当前显示层仍使用OLED坐标和字库，还没有接入串口屏或引入通用图形框架。

## 3. 函数声明、定义和调用有什么区别

```c
/* LED.h里的声明：告诉调用者函数存在及调用方式。 */
void LED_Display(void);

/* 定义现在位于Display.c：告诉链接器函数的实际实现。 */
void LED_Display(void)
{
    /* 读取AppConfig当前模式，执行原OLED绘制。 */
}
```

函数名并不要求其实现必须与同名模块放在一起。调用者包含声明后可以正常编译，最后由链接器找到唯一的定义。本轮保留LED_Display/Bump_Display的原名称、签名和声明，已有Refresh2_Data/Refresh3_Data调用位置不变。

因此这是兼容的分步迁移：先把实现集中管理，不同时重命名所有入口，也不要求上层调用者一次性重写。

## 4. 模式绘制具体保留了什么

两个函数继续直接读取AppConfig_Get()->led_mode/bump_mode，不读取一个脱离控制状态的显示副本。

| 项目 | LED模式 | 水泵模式 |
|---|---|---|
| 原入口 | LED_Display | Bump_Display |
| 两个汉字的x参数 | 64、80 | 54、72 |
| y参数 | 3 | 3 |
| 模式0字库索引 | 10、11 | 10、11 |
| 模式1字库索引 | 8、9 | 8、9 |
| 模式2字库索引 | 12、13 | 12、13 |

每种合法模式依原顺序画两个字，其他模式值沿用原不绘制分支，没有添加默认文字。上述是OLED驱动的原位置参数，不把y参数重新解释成像素行。

页面中的标签、字体大小、传感器数字格式、参数格式、估算补水量的一位小数、空格清尾及刷新调用顺序全部保留。当前字库内容也没有改动。

按键扫描/事件、TIM1内泵计时、传感器服务、参数保存、云端下发/上报、WiFi和OneNET实现保持原样。读取模式后画字不会设置模式或标记参数保存。
