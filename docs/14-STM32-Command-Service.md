## 1. 目标与分层

把命令规则从OneNET解析函数中抽出，将来更换主控或通信入口时可以保留命令契约和测试。

```text
MQTT帧 → onenet.c核对topic和长度
       → onenet_command.c解析OneJSON、生成应答
       → app_commands.c适配当前配置和LED动作
       → mw_command.c检查命令、生成目标状态
```

mw_command只依赖标准C头文件。app_commands仍依赖当前AppConfig和LED，是适配层，不宣称整个执行过程已与硬件完全独立。本轮先让OneNET接入新服务，板载按键继续走原AppConfig路径。

## 3. 命令契约

```c
CommandEntry command = { COMMAND_TEMP, 26 };
AppCommandResult result = AppCommands_Execute(&command, 1);
```

CommandEntry相当于一个与网络无关的“修改哪个参数、目标是多少”的结构体。其他输入入口以后可以构造同样的数据，不必拼OneNET JSON。

| 属性 | 取值 |
|---|---|
| led | 0关闭、1常亮、2自动 |
| bump | 0关闭、1脉冲、2自动 |
| CO2threhold | 350～4000 ppm |
| droughtthrehold | 0～100%，不能超过湿润阈值 |
| moistthrehold | 0～100%，不能低于干旱阈值 |
| tempthrehold | 0～100℃ |

保留全部现有标识符和协议值，严格区分大小写。没有增加PID参数、手动PWM等新的云端命令。

## 4. 执行前检查与批次

每批最多6项。先解析全部字段，再用当前配置生成候选目标，检查未知属性、重复属性、整数类型、数值范围及最终土壤上下限关系，全部合法才执行。

例如led=1与tempthrehold=-1放在同一批次，整批拒绝，LED也保持原值。土壤从30/75整体修改到80/90合法，执行时先扩高端；整体降低时先降低端，避免AppConfig对中间状态的钳制。

**行为变化：云端单独把干旱阈值设为高于当前湿润阈值时，现在明确拒绝并保持原值。** 原来AppConfig会钳制到另一端，却统一回复成功。板载按键的既有钳制规则保持原样。

这里保证参数不合法时执行前拒绝，不保证GPIO硬件故障、执行中掉电等情况下的实体事务回滚。Config_Set返回拒绝等内部异常使用500反馈；仍需实物验证。

## 5. 应答结果

| 设备应答码 | 含义 |
|---|---|
| 200 | 参数合法并成功处理，包含值原本相同 |
| 400 | 类型、范围、未知/重复属性、上下限冲突等请求错误 |
| 500 | 配置读写入口等内部处理异常 |

msg使用固定ASCII原因，避免OLED/协议编码混用。JSON不完整、过长/过深、没有唯一可信数字消息ID、回复缓冲不足时不执行，也不编造ID回包。

同值成功不会重新标脏、调用LED模式切换或重置PID，但请求一次新上报，便于App取得新时间的实际快照。设备200仍不是物理负载或EEPROM已经落盘的证明，原延时保存策略保留。

## 6. 上报调度

原5秒周期负责SensorService_Poll和周期上报。事件上报有独立的1秒最小尝试间隔，要求当前MQTT连接有效；不会因为连续控制而不断推迟5秒采集。

主循环先处理收到的命令，调用现有控制函数，再上报当前快照。现有OneNet_SendData接口返回0成功、1失败，主循环明确比较等于0后才清除待上报标记；失败/离线时保留请求，不进行无间隔发送。成功仅表示现有发送接口成功，不等同平台持久化确认。

温湿度不会因每条命令被额外高频采集；上报中的读数仍可能是上一次正常采集值。网络重连框架没有重构，不能称为已完成非阻塞AT状态机。

## 7. JSON边界与旧库修正

实际命令输入小于256字节，协议接收不再截断长帧后继续处理；topic必须完整匹配当前产品和设备，嵌入NUL的原始帧拒绝。解析前限制嵌套深度，数字ID限制为1～63个数字，并拒绝JSON编码的NUL，避免C字符串截断歧义。

测试复现了旧cJSON会把单独负号、缺失指数数字等畸形输入当成数值。现要求数字有实际数字位、禁止前导零、指数符号后必须有数字；同时给指数累积设置上限，并在旧valueint转换前处理NaN/越界值。

这只修改数字解析的边界，不升级整套第三方库。原cJSON的5条编译警告仍保留，不宣称完成了完整库安全审计。
