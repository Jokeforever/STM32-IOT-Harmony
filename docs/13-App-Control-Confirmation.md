## 1. 解决什么问题

旧代码在设置接口返回后，立即把LED/水泵模式设为目标，阈值则直接覆盖properties中的value，且沿用旧time。这样目标值看起来像实际状态，缓存、全部属性和页面返回值也可能含有尚未上报的假快照。

本轮把目标与读数分开：实心模式按钮、卡片和全部属性只显示实际查询结果；发送中的目标用描边和文字反馈，不覆盖properties。它也是未来更换主控/网络模块时可复用的App层规则。

## 2. 四种证据不要混淆

| 观察 | 能说明什么 |
|---|---|
| HTTP正常返回 | 请求获得了HTTP响应，仍需检查业务结果 |
| 外层code=0 | 平台接口返回成功，继续检查设备应答 |
| data.code=200 | 设备通过当前协议返回成功应答，不是实体负载测量结果 |
| 新属性上报的值匹配目标 | 查询到了比请求前更新的目标属性值，界面可展示该实际快照 |

本轮依据OneNET官方[设置设备属性](https://iot.10086.cn/doc/aiot/fuse/detail/1418)核对：外层code与设备端data.code分开，设备回复的id/msg也在data中。当前旧版接口地址及POST字段保持原状，不使用其他平台接口，也没有新增物模型属性。

真实固件当前在处理分支统一回复200，且未将每个AppConfig_Set的返回值细分进应答。因此“设备已应答”不能直接叫“设备已执行”。新上报匹配也是状态证据，当前协议没有把某条上报与某条控制请求的id关联起来，不能证明严格因果，更不能证明继电器触点、水流、灯具实际输出或EEPROM已经写完。

## 4. 状态机

| 阶段 | 界面含义 | 同属性能否再次发送 |
|---|---|---|
| SENDING | 发送中，尚未得到明确响应 | 否 |
| WAITING | 已返回，等待新上报；注明是否收到设备应答 | 否 |
| MATCHED | 上次目标已匹配新上报 | 是 |
| ACKNOWLEDGED | 脉冲命令已获设备应答；当前模式看实际上报 | 是 |
| TIMED_OUT | 等待上报超时，结果未确认 | 是，只有手动操作才再次下发 |
| REJECTED | 平台或设备明确返回非成功码 | 是 |
| UNCERTAIN | 网络/格式等异常，没有可靠结果 | 是；程序不自动重发 |

每个ControlRequest记录编号、属性名、目标、发送前属性时间、开始/响应时间、期限、应答标记和消息。同属性只保留最近请求，不为每次轮询增加记录；不同属性独立跟踪。发送过程共用loading，防止重复点击或GET/POST互相重叠。

数据流：

```text
用户选择目标 → 保存请求前属性时间 → 发送一次POST
           → 接口/设备明确拒绝：显示拒绝
           → 传输或格式异常：显示结果未确认
           → 正常返回：记录设备应答 → 短时GET查询
                                      → 新上报值匹配：完成
                                      → 等待30秒仍未匹配：超时
```

## 5. 什么数据可以确认

必须同时满足：请求已经收到响应、这次查询开始于响应之后、目标属性自己的time比发送前更新、该属性value完整解析后与目标一致。

- 不能用温度或其他属性的新时间确认LED。
- 不能用旧time下相同的值确认；即使目标原本就是当前值，也需新上报。
- 不能用手机时间补造属性上报时间。这里只比较同一个属性前后两个云端time，避免将手机与云端时钟差直接当作失败。
- 缺失time、空值、1abc这类部分数值不确认。
- 新上报暂时仍是旧值时保持等待，不马上判失败。
- 超时或网络结果不明后，后来真正取得新匹配上报，可以补记匹配，不重新发送控制。
- 老请求的迟到回包按编号匹配，不覆盖同属性后来新建的请求。

所有条件通过后，提示“新上报值已匹配”，而非“硬件动作已经测量确认”。

## 6. 脉冲灌溉为什么不同

bump=1会按既有固件逻辑运行一段时间后自动恢复0。若轮询时脉冲已经结束，查到0本来就合理，不能死等持续模式1。

因此收到设备200应答后，脉冲请求显示ACKNOWLEDGED，并立即查询当前属性。它不把按钮强制高亮在1，也不宣称已经测到实际出水。缺少设备应答时仍等待可用的新上报，无法确认则超时。泵/风扇/继电器实体负载测试继续暂缓。

## 7. 定时器、导航和存储

正常10秒自动刷新保留。等待控制结果时，详情页临时每2秒检查一次，GET仍走同一loading保护；收到响应后等待属性最多30秒。发送过程本身保留HTTP超时，并有请求结果未确认的兜底。

关闭普通自动刷新不取消一次已经开始的控制确认。这是有限时间的确认查询，不代表恢复了持续自动刷新。确认结束或离开详情页会清理临时定时器，不自动重发POST。

控制记录以monitorControlRequests保存在AppStorage运行期内存中，没有加入PersistentStorage。返回首页时，首页原有成功查询也可推进确认；重新进入详情会恢复记录并按原期限继续或显示超时。进程退出后不恢复这些请求，也不重发控制。

详情页使用页面代号检查异步回包。离开后，迟到GET不再更新已离开的页面和读数缓存；迟到POST只更新运行期请求记录，不操作旧页面、不重启查询。重新进入后再用新页面显示。

新控制状态不进入cachedAppState；旧快照、趋势缓存v2与10倍缩放逻辑保持原结构。阈值不再写本地假属性，全局缓存也只接收查询结果。

## 9. 五项用户验收清单

1. **LED请求与实际状态分开**：板子在线，改变LED模式。先看到目标提示/描边，原实际上报模式保持；收到新上报后实心按钮切换，提示新上报值已匹配。等待时同属性不能重复下发。
2. **阈值与全部属性一致**：调整温度阈值1℃或CO2阈值100ppm。等待时目标显示在提示中，数值及全部属性保持原上报值；新上报后一起更新，并与OLED/OneNET一致。
3. **关闭普通自动刷新后仍完成确认**：关闭详情页自动刷新，再改变LED。应通过短时确认查询完成，不需要重新进入页面；完成后不会继续每2秒确认。
4. **离线结果可信**：板子断电，等待超过约30秒并刷新。控制应禁用，最后上报仍可查看。短暂断连时如果请求被拒绝或无明确结果，界面不能直接把目标当作实际值；不自动重发。重新上电刷新后可恢复操作。
5. **页面切换不重复执行**：发出LED请求后返回首页再进详情，显示保存的请求/实际上报结果，原请求不重新发送；正常刷新、全部属性、趋势和10倍缩放继续正常。无需对暂缓的实体负载做测试。

有异常时记录目标、提示原文、当时实际值和设备是否在线，便于区分API应答、上报时序、界面刷新三类问题。
