## 1. 为什么先做这一项

之前曲线把每次成功查询得到的温湿度放进数组。问题在于：查询成功，只说明 App 取得了云端当前保存的属性；同一条设备上报可能被查到多次。设备断电之后，云端仍可能返回之前的属性，这些旧值不应不断形成新趋势点。

因此本轮把曲线的含义从“最近几次查询值”改为“本机实际获取的最近几条有效上报”。这对以后更换 MCU、网络模块或者传感器也适用，因为规则建立在属性、时间和值上，不依赖具体 GPIO。

## 2. 三种时间分别是什么

| 时间 | 来源 | 当前用途 |
|---|---|---|
| MCU 相对运行时间 | HAL_GetTick，单位毫秒 | 采集调度、PID 的 dt、配置延时写入 |
| 云端属性上报时间 | 查询结果中每个属性的 time，沿用项目现有毫秒时间契约 | 趋势点去重、横轴、设备上报时间展示 |
| App 最后同步时间 | 成功查询时的本机日历时间 | 表示 App 最近一次取得云端快照 |

HAL_GetTick 从启动累计，不能直接当作日历时间。当前 STM32 没有给每次传感器采样附带独立日历时间；本轮使用的是云端属性上报时间，不能称为精确的 MCU 采样时刻。无需新增 OneNET 属性。

首页与详情页同时显示“最后同步”和“设备上报”。后者取当前属性快照中合法 time 的最大值，代表最近一项属性的上报；温度曲线只用 temp.time，湿度曲线只用 humi.time。控制属性时间更新不会凭空生成温湿度样本。

## 4. 从数值数组到带时间的结构

旧结构只有 number[]，例如 [24, 24, 25]，无法知道中间两个 24 是同一条上报被读了两次，还是两次不同上报。

现在每个点是：

```ts
export interface TrendPoint {
  time: number;
  value: number;
}
```

例如 { time: 1794096000000, value: 24 }。可以把它理解为 C 中保存时间和值的结构体。两个字段一起构成一个趋势样本；判断重复看时间，不能只看 value。同样的温度持续一分钟，也应记录期间实际取得的不同上报。

温度和湿度分别保存自己的数组，每条曲线最多 20 点。数组通过新赋值交给 @State，再传入 HistoryChart 的 @Prop，保持本项目已有的数据刷新方式。

## 5. append 的判断规则

1. 找到指定属性，温度为 temp，湿度为 humi。
2. 如果有 sensor_status，则按 bit0/bit1 分别判断温度/湿度有效；缺失该属性时兼容旧固件，允许记录。非法状态值不作有效处理。
3. value 必须是非空字符串，转换后是有限数值；例如 24abc、NaN、Infinity 都拒绝，不使用 parseFloat 的部分解析行为。
4. time 必须是正整数毫秒且位于 JavaScript Date 支持范围；缺失时跳过，不用 Date.now 补造时间。
5. 时间比已有最后一点更旧：忽略本次点，防止曲线倒退。
6. 时间相同：替换最后一点的数值，不增加点数，支持云端同时间值修正。
7. 时间更新：追加；超过 20 点时丢掉最旧点。

normalize 会过滤无效缓存点、复制数据、排序并合并重复时间。它不修改调用者的原数组。

这里的“有效”是趋势记录资格，依据已有有效位、数值和时间格式。它不证明传感器物理准确，也未增加光照/土壤/水量拔插检测；曲线绘图范围仍为温度 0～50℃、湿度 0～100%，超出范围仅在绘图时限幅，原始样本值保留。

## 6. 两个页面如何共享缓存

```text
查询完成 → 页面获得 properties
         → 从 AppStorage 取最新 cachedAppState
         → TrendHistory.collect 合并历史
         → 保存 properties、时间、版本和两组历史
         → 详情页给 @State 历史重新赋值 → 子图表刷新
```

首页也收集历史，所以不必一直停在详情页才有曲线。在查询结束后再读取共享缓存，可以避免较旧页面持有的历史数组直接覆盖另一页面已经新增的点。

这解决的是趋势数组的合并，不代表所有跨页面 HTTP 请求完成顺序都已重构。原同步、自动刷新、控制、阈值处理流程保留；控制请求与设备确认状态仍为后续工作。

## 7. 缓存版本与旧数据迁移

cachedAppState 继续使用现有 AppStorage/PersistentStorage。新增 historyVersion: 2，温湿度历史改为 TrendPoint[]，properties、lastSyncTime、lastReportTime 字段保留。

旧 number[] 没有可靠时间，无法诚实恢复横轴，因此不补造它们的时间。首次升级时旧曲线点被丢弃；如果旧缓存的当前属性带合法时间且传感器有效，则用这份属性建立一个可靠起点。之后正常积累新上报。版本 2 缓存恢复时会清理损坏点。

这是 App 历史缓存版本 2，与 STM32 EEPROM 配置版本 v2 没有联系；App 首页版本文字仍为 v13，本轮未变更安装包版本。

PersistentStorage 保留本机已观察的历史；清空 App 数据或卸载仍会丢失。本轮没有调用云端历史查询 API，也没有后台采集服务，App 未运行期间的上报不会被自动补齐。设备约 5 秒上报，App 通常 10 秒轮询，图中只包含轮询实际取得的快照。

## 8. 横轴为什么不再等距

假设三点上报时间为 0、1、10 秒，旧索引横轴会画成 0%、50%、100%，容易误导对变化速度的判断。

现在在绘图区内使用：

```text
x = 4 + (绘图宽度 - 8) × (当前时间 - 最早时间) / (最晚时间 - 最早时间)
```

得到大致 0%、10%、100% 的位置。首尾各留 4 的边距。少于两个点时显示等待提示；横轴下方显示首尾上报时间。长时间断连后恢复，时间间隔会体现在点的位置上；连线是可视化连接，不代表断连期间存在测量数据。

## 10. 本轮五项实测清单（等待用户确认）

1. **新上报能形成曲线**：板子在线，打开 App，再进详情，等待两次以上成功轮询。温湿度各有至少两个不同时间点后显示曲线；时间和值与最近收到的上报相符。

5. **恢复与回归**：重新给板子上电，收到新有效上报后曲线继续，最终最多 20 点。LED 模式、原阈值设置、手动刷新和自动刷新开关仍按原功能工作。无需测试暂缓的水泵/风扇/继电器实体负载。

## 11. 曲线放大与纵轴缩放（同日新增）

用户反馈上节五项检查“应该通过”，并展示实际曲线。本轮只继续改善图表显示；放大功能另行等待实际操作确认。

每条曲线标题右侧有“放大”按钮，打开全屏覆盖视图，顶部“关闭”返回原详情页。可在空气温度/空气湿度之间切换，不必退出重进。放大绘图区高280，原卡片绘图区增至128，均按实际容器宽度布局。

两种纵轴模式：

- **局部放大（默认）**：按当前数据的最小/最大值和留白确定量程，温度最小计算跨度4℃、湿度10个百分点，防止恒定数值形成零量程或把微小变化无限放大；实际最终范围还受刻度取整、量程边界影响。
- **完整量程**：温度0～50℃，湿度0～100%，方便看整体变化，普通卡片也保持这一模式。

例如21～23℃的样本，局部纵轴约19～25℃，比固定0～50℃容易观察。所有模式都明确显示左侧刻度、单位、首尾上报时间和最新数值；局部模式另有文字提示。新数据进入或最旧点离开时，局部量程可能变化，比较绝对变化幅度应同时看刻度，或切回完整量程。

数据不做平滑拟合、不改变缓存中的读数。时间横轴仍按实际间隔，虚构点不会加入历史。完整量程保留原超范围绘图限幅规则，局部模式包含当前样本的实际范围。

纯逻辑displayRange位于TrendHistory，plotPoints增加可选height参数；不传高度时仍保留原96的坐标规则。图表组件通过@Prop接收样本、autoFit与plotHeight，父页面用@State保存弹层开关、当前指标和缩放模式。没有新建另一套轮询器；详情页原自动刷新与“立即刷新”更新同一份历史，大图直接显示它。

新增8个场景20项检查，涵盖扩大高度、恒定值、截图中的小幅温变、湿度两端、负温、数据不变与样本包含范围。加上此前回归，总计53场景84项通过；ArkTS编译通过，保留3条既有服务警告。尚未用新HAP或模拟器实际操作本轮大图。

建议本轮实际核对三项：

1. 分别从温度/湿度的“放大”进入，图表和左侧刻度完整显示，能切换指标，关闭及系统返回后可再次打开并回到原详情位置。
2. 切换“局部放大/完整量程”，曲线视觉幅度和刻度随之改变，最新读数与历史点数不因切换而变化；恒定读数仍正常显示。
3. 保持大图打开并让传感器数据变化，自动刷新开启时可继续更新；关闭自动刷新后，使用大图内立即刷新也能更新，未额外产生定时器或重复点。

## 12. 连续滚轮、滑条与拖动（当前实现）

上一版只有局部/完整量程切换，之后新增连续缩放；用户现要求将最大倍率由100倍下调至10倍。第11节保留为前一版说明；坐标绘制与交互规则以本节为准。

### 使用方法

1. 点击普通温度/湿度曲线右上角“放大”。
2. 在大图选择“数值”（默认）、“时间”或“双轴”。鼠标停在绘图区内滚轮向前放大、向后缩小；也可以拖动1×～10×滑条或在触屏上双指捏合。
3. 鼠标左键或单指拖动图内曲线，查看放大后的其他位置；图外仍可正常滚动页面。双击图内或点“重置”回到最新全图。
4. “局部放大/完整量程”仍决定初始范围，切换时清除手动视窗，之后可在该基准上继续缩放。10倍是相对所选初始范围，不意味着传感器精度提高。

滑条为对数映射，便于在低倍率细调，1倍与10倍是两端。时间/数值倍率分别显示；在“双轴”模式下滑条以数值倍率为参照，按同一比例调整两轴，已到上限的一轴保持上限。最新数值与缓存点数不随缩放变化。

### 数据与视窗分开

TrendViewport在DeviceModels中定义timeMin/timeMax/valueMin/valueMax。TrendHistory新增viewportFor、zoomViewport、panViewport、viewportPoints和wheelZoomFactor，均不调用UI或网络。

滚轮以光标所在位置为锚点；滑条优先围绕当前视窗内的最新点缩放；双指以开始时的中心位置为锚点。缩放后可见跨度限制在基准的1～1/10，平移限制在该基准边界内。

数值轴放大后固定该轴范围，时间未缩放时仍跟随新上报。时间轴放大后固定所看的时间窗，新上报仍接收但可能出现在窗外；新的值也可能超出锁定纵轴。重置即可解除锁定并回到当前最新范围。不为保持曲线可见而偷偷改动传感器读数。

viewportPoints保留窗外的原始投影坐标，由图表clip裁剪线段，避免将所有超界点压成沿边界的假水平线。高倍率下刻度增加小数位，时间窗小于10秒时显示毫秒。画面中的连线仍只连接本机已取得的上报，不会提高实际采样率或补回漏掉的数据。

### 输入处理与兼容范围

项目使用本机SDK22中的onAxisEvent/AxisEvent，垂直轴值控制滚轮倍率，支持触控板轴捏合比例；触屏使用PinchGesture与PanGesture。轴事件与拖动手势分开处理，避免同一滚轮同时缩放和平移。只有放大图注册交互，普通图保留页面原有滚动。

API核对依据为本地SDK声明及官方[轴事件文档](https://developer.huawei.com/consumer/cn/doc/harmonyos-references/ts-universal-events-axis/)、[OpenHarmony轴事件说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkui/arkui-ts/ts-universal-events-axis.md)。没有使用SDK22之外的新接口。
