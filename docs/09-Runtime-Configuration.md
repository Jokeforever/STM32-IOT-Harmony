# 运行配置统一：学习说明与本轮验收

代码修改与编译日期：2026-11-01。用户验收与同步日期：2026-11-07，五项检查均通过。

## 为什么继续做这一步

上一轮把传感器读数统一为SensorData。这一轮把“希望设备怎样工作”的参数统一为RuntimeConfig。
现在项目中有三类对象：

| 对象 | 保存什么 | 谁负责更新 |
|---|---|---|
| SensorData | 温湿度、光照、土壤、CO2和有效位 | 传感器采集服务 |
| RuntimeConfig | LED/泵模式、阈值、手动PWM、PID目标/系数/死区 | AppConfig参数服务 |
| 运行状态 | PID积分/上次误差、水泵计时、页面选择、网络状态等 | 对应业务模块 |

例如温度28°C是测量值，温度阈值30°C是配置，风扇此刻是否开启是控制结果。
把它们区分清楚，可以减少代码误写，也便于以后更换MCU、传感器或存储设备。

## 改动了哪些文件

- `modules/app/inc/app_config.h`：参数结构、参数编号、范围说明和对外接口，只包含标准整数类型。
- `modules/app/src/app_config.c`：唯一运行配置实例、默认值、范围/关联检查、保存通知和模式历史。
- `modules/middleware/src/mw_config.c`：把运行参数映射到旧存储记录；继续负责双槽、CRC32、版本迁移、延时保存。
- `Core/Src/Key.c`：保留按键扫描和计时算法；调整参数改为统一增减入口，模式切换通过LED_Set/Bump_Set。
- `Core/Src/LED.c`：目标、系数和死区从配置读取；LED_Control只保留运行状态。
- `Core/Src/bump.c`、`jdq.c`、`beep.c`、`Display.c`：从统一配置读取模式或阈值。
- `Core/Src/usart3.c`：不再定义/重置业务CO2阈值，串口接收继续只负责传感器帧。
- `Core/Src/main.c`：在外设业务初始化和启动计时中断前初始化运行配置。
- `onenet/onenet/src/onenet.c`：云端阈值请求交给统一参数服务，保留原来的属性名与应答协议。
- `tests/run_control_regressions.py`：扩展实际C代码回归与旧EEPROM记录测试。

## 统一参数怎么读取和修改

```c
const RuntimeConfig *config = AppConfig_Get();
uint8_t temperature_limit = config->temp_threshold;

/* 指定一个值，例如收到云端温度阈值。 */
AppConfigResult result = AppConfig_Set(APP_CFG_TEMP_THRESHOLD, 30);

/* 相对调整，例如本机按键按步长加2。 */
AppConfig_Adjust(APP_CFG_TEMP_THRESHOLD, 2);
```

`AppConfig_Get`给出只读实时视图，外部不能通过它直接给参数赋值。
`AppConfig_Set`检查范围和关联关系，实际改变后才通知Config_MarkDirty。
`AppConfig_Adjust`先检查离上下限还剩多少空间，再相加，避免无符号下溢和大增量溢出。

返回值分为拒绝、未变化、已变化。重复设置相同值不会重新启动保存等待时间，也不会反复写EEPROM。
PID目标/系数/死区改变时会清除旧积分和历史；相同PID值不会反复清除。

模式仍使用原来的0/1/2。LED硬件切换沿用LED_Set加Mode_Switch的现有路径；泵的输出仍由原控制循环处理。
按键和云端通过同一参数服务，但网络包解析、传感器帧解析和真实负载控制仍是各自模块的职责。

## 参数范围与单位

| 参数 | 允许范围 | 单位/说明 |
|---|---|---|
| LED模式 | 0～2 | 关闭、手动常亮、自动 |
| 水泵模式 | 0～2 | 关闭、脉冲、自动 |
| 手动PWM | 0～100 | 百分比；原本按键到100后回0的操作保留 |
| 温度阈值 | 0～100 | 摄氏度 |
| CO2阈值 | 350～4000 | ppm |
| 光照低/高阈值 | 0～9999 | lux，低≤高，继续沿用原项目阈值范围 |
| 土壤低/高阈值 | 0～100 | 百分比，低≤高 |
| PID目标 | 0～999 | lux |
| PID死区 | 0～200 | lux |
| PID Kp/Ki/Kd存储值 | 0～10000 | 真实系数乘1000，即实际0～10 |

超出总范围的指定值被拒绝。光照或土壤在总范围内但跨过另一端时，会限制到另一端，沿用原云端土壤阈值的处理方式。
例如土壤高阈值75，尝试设置低阈值90，实际低阈值限制为75。

本机增减也受上述规则约束。例如温度99加2得到100，CO2阈值375减100得到350；
光照低阈值950、高阈值1000，低阈值加100后得到1000，不会越过高阈值。

PID配置已集中，但本轮没有增加OneNET PID属性或App PID编辑界面；现有云端可调范围仍按原物模型。

## 为什么EEPROM不会要求清空

RuntimeConfig是运行时对象，DeviceConfig仍是独立的旧v2存储记录，不把运行结构直接写入EEPROM。
mw_config逐字段做转换，原来的magic/version/size/sequence/CRC和A/B槽规则保留。

v2记录仍是48字节，CRC字段偏移44；v1记录仍是32字节。
这些尺寸在真实目标编译器上也有编译期检查，防止未来改结构导致静默破坏旧数据。
通过独立构造的旧v2二进制记录验证了读取、保存后的逐字节一致性，v1自动迁移也通过主机测试。

已有有效EEPROM参数继续优先，包括以前保存的PID目标500，不会强制变成默认200。
保留的土壤ADC字段仍按原逻辑处理；本轮没有增加ADC校准功能或改变传感器换算。

## 水泵中断为何单独处理

原计时中断会在脉冲结束时把水泵模式改回关闭。现在这个行为通过
`AppConfig_CompletePumpFromISR`完成，只允许把脉冲模式1改为关闭0。
这个接口不调用Config_MarkDirty、HAL计时或EEPROM，不改变原脉冲结束的保存策略。

主循环提交泵模式时，几个读/比较/写操作使用很短的中断屏蔽区，结束时恢复之前的PRIMASK状态。
保存通知发生在临界区外，避免中断恰好完成脉冲时丢失主循环提交。
除这个模式字段外，配置仍只在主循环修改；Init/Restore只用于启动阶段，须在启动计时中断前完成。

因此运行配置结构和接口头是标准C契约，但当前服务实现仍依赖PID重置、保存通知和Cortex-M中断原语，
尚未宣称它已经完全独立于平台。将来更换主控时，需要继续检查这些适配点。

## 这次实际改变的边界行为

1. 光照、温度、土壤、CO2等按键步长跨界时，限制在合法范围内，修正原来的越界/下溢情况。
2. 本机模式按键现在也通知延时保存，和云端模式设置走相同入口。
3. 只有实际参数变化才触发保存通知，反复按住上限或重复云端设置不延后保存。
4. PID配置变化统一清历史；PID计算公式、原脉冲计时、水泵补水量估算、采样和上报周期保留。

云端非法值仍不应用；原有set_reply协议没有改成逐属性错误报告。
同一云端消息同时改多个字段仍按原顺序处理，本轮没有新增整组事务提交功能。
温度设置页操作后回到首项、本机手动PWM100后回0等原操作习惯保留。
